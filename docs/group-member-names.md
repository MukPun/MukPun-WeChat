# 群成员昵称与群名片

2026-10-27 已部署群成员名称透传。微信消息仍逐条转发，用户数字 ID 和群路由保持稳定。

## 数据来源与转发

固定 agent-wechat beta.8 的消息记录只有 `senderId`，没有昵称。联系人目录提供 `nickname`、`displayName`，群成员目录提供 `displayName`、`roomDisplayName`。中转按当前消息的真实发言人 ID 精确匹配，不能按同名联系人猜测身份。

`sender_names.Resolver` 仅查询本地目录的 GET 接口。单次解析最多 0.8 秒，按群和成员缓存成功结果 300 秒、缺失结果 30 秒，最多 1024 项。超时、目录缺失或非法名称不会中断正文转发。昵称或名片最多 256 UTF-8 字节，拒绝控制字符及用内部 ID 冒充名称。

名称通过管道进入 OneBot 的 `sender.nickname`、`sender.card`，不拼入消息正文。成员名称有界保存于项目私有 SQLite 的 `member_names` 表；群名片按群和用户共同索引。`get_group_member_info`、`get_stranger_info` 使用这些已观察到的资料。查不到名称时保留原有占位名；不声称提供完整成员列表。

昵称不参与源消息去重摘要。改名、补齐资料或重启不会使同一条消息重复转发，正文变化仍会被校验。

## 本地目录缺失

微信实时消息可能只建立最小联系人记录，不自动补齐群成员资料。排查时，一个群未缓存成员目录，另一个目录为空；最近六名发言人也只有 ID。对已观察群执行一次定向成员资料刷新后，实际取得 30 个成员昵称、14 个群名片，六名发言人均有真实昵称。

定向刷新接口是 `POST /v1/accounts/{account}/groups/{room}/members/refresh`，随后读取返回的操作状态。它会更新本地资料，不能当作普通本地 GET。中转的逐消息解析不会自动触发全量通讯录同步或成员刷新。新群未缓存资料时可能暂时使用占位名，需要定向补齐该群资料。旧 AstrBot 历史记录不会自动回填。

## 同时发现的会话恢复故障

排查期间 Native 意外退出，发送数据库停在 16 MiB 单文件上限，并留有 SQLite 回滚日志。私有副本按原日志恢复后完整性检查通过，147 条已接受发送记录及最近发送绑定保持完整。单文件限制可能触发了该次退出，原进程没有留下可确认信号的日志。

已修正恢复流程：仅在私有恢复副本中允许 SQLite 执行正常事务回滚，随后启用只读查询、完整性检查和原有待发送门禁，再启动 Native。原始快照不会被直接改写。Native 单文件上限调整为 32 MiB，与既有 32 MiB tmpfs 总存储边界一致；未扩大临时盘、内存或网络范围。未完成或不确定发送仍会阻止恢复。

## 图片转发边界

全群模式在开启图片输入时直接上报普通群图片。微信 `type=47` 表情包仍按既定范围跳过，不属于已实现的普通图片 `type=3`。2026-10-28 的两条群图片样式消息实际为 `type=47`，在进入 AstrBot 前被跳过；没有改动此策略或插件配置。

AstrBot 群聊插件自身的图片应用范围也会影响后续处理。例如 `at_only` 只处理真正 @ 机器人的图片，非适用范围的纯图可能被插件丢弃，图文混合消息可能仅保留文字。排查时应同时核对 Native 消息类型、中转图片计数与 AstrBot 原始记录，不能只凭模型历史缺少图片段判断中转失败。
