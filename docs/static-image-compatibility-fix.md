# 常见静态表情图片兼容修复

2026-10-27，针对用户 11:49:10 提供的 `unsupported_message_segment / echo.seq=144`。

## 已定位的兼容缺口

插件日志显示这次选择了 `happy` 分类并发生一次发送失败，没有保存随机文件名，因此无法追溯当次准确素材。AstrBot 适配器把 `Image` 转为标准的单张 base64 OneBot 图片段，图片源与图库为同一数据挂载。

旧桥的源图片限制为 1MiB、1024 边长和 1MP。该分类 20 张图有 7 张不符合旧限制，包括 960×1280、1254×1254、1280×1214 JPEG/PNG，以及 1.1～1.9MB PNG。不能用此前 AW01 小图片的成功推断这些日常素材也可发送。

## 修复内容

- 静态源图片支持 PNG、JPEG、WebP，最大 2MiB，宽高各不超过 2048，总像素不超过 2×1024×1024。Native IPC 单帧仍为 256KiB、原始分块64KiB；WebSocket action 独立上限4MiB，可容纳2MiB图片的base64编码。
- PNG 使用内存视图处理 IDAT，并以最多64KiB输出块校验解压数据及每行过滤字节，不在桥内保留整张解压像素。校验尺寸、CRC、解压总量及动画拒绝逻辑保留。
- 发送校验失败记录固定枚举原因、格式、字节数、尺寸及SHA；不记录图片内容、路径、URL、聊天正文或未知字段。API仍明确返回失败，不伪造成功，已拒绝图片不停止文本桥。
- 回执校验兼容 SDK 原样保留小体积 JPEG 的行为：保留时绑定源 JPEG 的准确尺寸和 SHA；重编码时仍绑定1280边长上限、宽高比、服务器回执、三份媒体校验及本地投影。
- 现有进程内存、CPU、Native32MiB私有存储、上传前容量检查、持久动作去重及未知结果不重试规则保留。未修改AstrBot、图库、SDK、Docker、FRP或宿主网络配置。

GIF、动图、原生sticker、图文混合、多图仍不在本次单张静态图片输出范围。2048×2048图片超出总像素限制，继续在提交前拒绝。图片输入维持128KiB。

## 复验后发现的独立失败与恢复

复核时发现另一次76270字节图片请求在SDK的preparing阶段失败，错误枚举media_processing_failed，已产生320×320的准备信息，但没有上传读回确认、Native发送回执或消息投影。该失败请求与已经交付的640×640图片是不同作业；未把失败请求记成accepted。

旧客户端把创建本地作业的POST已接受当作“微信提交已经发生”，因此将这一确定的提交前失败归为未知结果，停止桥，并因审计待核对而出现4次自动恢复失败。已修复：终态failed且仍在preparing/uploading/readback、无serverMessageId和nativeReceipt时，按确定未提交处理；submitting/completed阶段的无回执失败仍保持未知结果保护。固定SDK在真正调用send_image之前才将phase改为submitting，见[固定版本实现](https://github.com/thisnick/agent-wechat/blob/v1.0.0-beta.8/packages/native-client-rust/crates/wechat-core/src/media.rs#L1944)。

新回归Linux226项全部通过，Windows Native模块22项通过（1项POSIX跳过）。恢复只修改3个经过摘要核对的文件；审计和动作库先保存到项目外root私有备份。已精确校验该失败作业的状态、阶段、次数、源摘要及目标摘要，将对应预留动作记为已知失败并保持去重，没有清空队列或重放消息。随后清理本项目桥的失败状态并恢复服务，Native登录进程、宿主网络和Docker/FRP基线不变，无新二维码。

静态图片实际交付已通过；个别素材仍可能被固定SDK的图片准备流程拒绝，底层media_processing_failed的具体原因尚未确认。此类已知失败现会返回失败并保留记录，不再停止文本桥；不承诺任意图片均可发送。

累计16次上传试运行预算及真实存储余量保护仍保留，尚未完成SDK缓存安全回收与长期图片服务验收。
