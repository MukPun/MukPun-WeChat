# 重启后忽略积压、优先实时转发

## 状态和用户要求

2026-11-17 用户明确：桥重启后不需要补发积压消息，忽略即可，只关心正常运行期间的消息转发。该要求覆盖此前“恢复时必须继续旧接收进度”的产品约束。本文记录已确认的需求和建议实现边界；尚未修改生产行为或启动当前停止的桥。

## 现有快照是什么

运行期捕获任务是生成恢复点，不是每五分钟执行一次恢复。它通过 Native owner 保存微信接入端的会话资料和数据库，复制桥库取得一致接收边界，再生成将归档、身份指纹、发送隔离账本版本和接收边界关联的恢复清单。正式周期为 300 秒。会话资料用于 Native 退出后的登录状态恢复；接收边界和去重保护还服务于旧的跨重启继续接收策略。桥的身份映射、动作幂等和审计另有持久数据，不能因不补消息而删除。

当前捕获失败会让恢复后端设置 requires_review，控制器据此停止整个桥。取消积压补投本身不会自动消除这条停机路径。2026-11-16 20:26:46 UTC 的直接证据是捕获子任务失败后进入保护，具体异常未保留；不能据此断言此次只是普通备份错误。

## 快照必要性和存储保留

现行 Native 运行资料位于受限进程的 tmpfs，见 `scripts/session_runtime_host.py` 的 `TemporaryFileSystem`。仅重启桥且 Native 继续在线，在功能上无需用快照重建微信会话；当前源码仍将清单准入纳入启动，必须调整实现，不能直接删文件绕过。若 Native 或宿主退出，tmpfs 内容会丢失，目前仍依赖磁盘保存的会话归档恢复原登录。用户放弃积压补投，可以移除相应的接收边界协调需求，不能据此删除唯一的会话持久化资料。未来如果改用可靠的私有磁盘数据目录，会话快照才可进一步降为可选备份；本设计尚未选择或实施这项存储改造。

保留策略由源码明确限定：

- `session_state_store.SnapshotStore.commit` 用 current/previous 两个固定槽轮换，新归档在 `.next.zip` 完成后原子替换，旧 previous 被覆盖；常规异常会清理 `.next.zip`，强制中断遗留由下次提交处理。
- `recovery_manifest.Store.publish` 在发布前后清理只由当前/上一代清单引用的归档和清单，正常完成后保留两代。发布中途失败可能留下候选，待下一次合法发布清理；这不是独立的按天清理 timer。
- 单归档的代码上限为 1028 MiB，数据源上限为 1024 MiB。这是单文件边界，不是整个磁盘或私有状态目录的总配额；生成、复制、校验期间还有临时占用。文件数量有限不代表总空间永远足够。
- 其他历史归档、人工运维和故障备份不由上述两个轮换器覆盖。不能将这些目录也描述为自动只保留两代；若要清理，须另外核对用途与恢复引用。

2026-11-17 仅统计文件元数据的实际观察：原始会话槽 2 份归档约 0.66 GiB，恢复清单目录 2 份约 0.66 GiB，合计约 1.32 GiB；其余私有状态目录另有 20 份归档约 1.44 GiB，尚未逐份判定用途，不能全部标为可删除。该私有状态目录实际分配合计约 2.90 GiB，磁盘可用约 284 GiB。没有读取归档正文、删除文件或更改服务；这些数字是当次统计，不是容量保证。

## 建议行为

1. 桥每次完整启动，在原账号身份和接收源核验通过后，建立明确的新接收起点。启动时已有的旧 Native 事件和上一次桥进程遗留的未交付输入不交给 AstrBot；不删除原始记录，记录跳过原因和数量。已 publishing/uncertain 的输入仍保留原状态证据，不自动重试。
2. 新起点形成后只接收后续事件；起点获取和订阅交接必须避免遗漏起点之后的新事件。这里的边界是 Native 事件流的可验证位置，不以本机时钟猜测事件新旧。已知的断网积压如果由 Native 在起点之后才导入，须在实现时核对其消息元数据和上游语义，不能仅凭游标承诺所有停机期间发送的消息都已排除。
3. 明确区分完整桥重启与同一运行代的短暂 WebSocket 重连。默认只在完整桥启动时放弃历史积压；运行期间短暂重连沿用本代的有界转发，不把每次网络抖动都当作清队列授权。
4. 微信会话保存保留，用于恢复原登录资料。身份映射、出站幂等、发送隔离和故障审计继续持久化；跳过入站积压不代表可以重发旧出站动作或把未知发送改成成功。
5. 会话备份或恢复点生成失败应明确记录阶段、固定错误码和脱敏诊断，并可重试/退避；已知为备份作业自身的失败不单独停止健康的消息转发。当前正在使用的身份、数据库或 IPC 完整性故障仍需单独处理，不能用一个通用 requires_review 混合所有失败。

## 方案取舍

推荐保留必要的会话保存，将跨重启补消息从默认转发职责中移除，并隔离备份失败。仅跳过旧输入的改动较小，但仍保留备份失败停桥的问题。直接删除全部快照/状态会同时失去会话恢复和发送幂等证据，不符合复用微信登录及不重复发送的现有要求。

## 实施核对与最小验收

正式实现前须核对 Native 最新边界接口、导入停机消息的语义、启动协调器、host 队列和 worker 重建路径，避免只改 SSE 游标却让 SQLite 旧 queued 消息继续发布。需要少量有效合成场景：重启不发布旧输入；起点之后的新输入交付一次；起点与订阅交接无空隙；同代 WS 重连不错误清理；备份任务失败保留诊断而健康转发继续；身份/持久状态故障不被当作普通备份失败忽略。无需为设计文档运行模型、发送真实微信消息或重跑全量测试。

备份失败的隔离还须覆盖 `scripts/session_runtime.py` 的 owner 周期保存路径：现行 `host.checkpoint()` 异常会转成 `checkpoint_failed` 并退出。只调整桥的 `RecoveryBackend` 不足以保证普通备份失败不会影响 Native；隔离失败时还须证明 freeze/thaw 正常释放，不能对未恢复执行的 Native 声称仍可转发。

## 登录资料直接持久化的后续讨论

用户进一步询问长期登录是否需要每五分钟做一次快照。现行在线 Native 使用活动资料，不靠读取快照维持连接；快照用于该易失资料环境退出后的恢复，并不是每五分钟续一次登录。`session_runtime_client.py` 启动 Native 已使用 `--data-dir`，因此可将完整私有资料目录改为可靠的磁盘持久化存储，让 Native 正常更新自己的密钥、profile 和数据库，快照仅承担可选灾备。五分钟频率反映当前 tmpfs 的恢复点取舍，不是微信登录本身的要求。磁盘保存不会替代服务器端的身份/信任判断，也不能只保存首次扫码时的一份令牌而丢弃后续资料更新。

对用户“长期会话、实时转发、重启忽略积压”的目标，建议进一步评估直接持久化目录。该建议尚未实施，也未迁移线上资料。实施时须同时处理随机 Native 用户的跨启动目录所有权或受控映射、独占写锁、SQLite/WAL 一致性、完整密钥与 profile、原进程退出证明以及 Native 出站队列的启动准入；不把私有目录暴露给 OneBot，不删除现有隔离或审计。原资源限制保持，盘上资料增长另有容量和维护边界。持久化成功后再退出“周期全量归档是唯一持久副本”的依赖，避免先停备份再迁移导致资料无可靠副本。正常停机可选备份、登录成功等事件触发备份、低频灾备的具体策略应在迁移设计中确定。
