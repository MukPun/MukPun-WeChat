# JPEG 尾随数据兼容与单笔未知图片隔离

## 2026-10-29 JPEG 格式误拒

00:12 的 `1400 unsupported_message_segment` 对应一张 29001 字节、455×433 的 JPEG。结束标记后存在 24 字节应用尾随数据，既有 Pillow 可完整解码；原桥要求文件最后两字节必须是 EOI，因而误拒。

JPEG 校验现按段长度和扫描标记遍历，确认扫描数据后存在真实 EOI；跳过 stuffed 数据、restart 标记与 marker fill，兼容渐进多扫描。源字节、完整源摘要均保留，不裁剪或重新编码。截断数据、段内伪 EOI、stuffed 伪 EOI、未开始扫描或无扫描数据的结束标记仍拒绝；大小、尺寸及静态图片限制不变。

发布复核补充了只有 marker fill 或 restart 标记、没有实际扫描数据的两个反例。先确认旧校验误收，再改为单独记录真实扫描数据；控制标记本身不计为图片数据。

真实素材仅在本机离线核对，没有写入仓库或作为发送测试；修改后的源契约和 Native 客户端构造校验通过，未调用上传、发送或模型。

## 隔离恢复约束

- root 私有 `forward-image-hold.json` 记录完整原审计的规范 JSON 摘要、准确 jobId、当前 Native PID/启动 ticks、批准时间和 `text_only` 模式。正常启动没有此记录时仍拒绝未知图片。
- `text_only` 仅在图片输出关闭、审计完全匹配、同一 Native 仍运行且连接正常时启动文字桥。隔离启动绕开所有可能恢复或启动 Native 的普通 `ensure_*` 路径；Native 退出或身份改变时失败停止。
- 其他文本未知、不同图片审计、修改后的目标/源/动作均不被此例外覆盖。未知桥动作和 Native 作业不改写；不清理队列、游标或上传预算。
- `text_only` 拒绝 `image-output enable`；只有用户随后明确授权恢复新图片，才能将精确隔离记录改为 `new_images`。任何隔离模式都拒绝可能重启 Native 的 `promote`。
- 状态明确显示 `quarantined_images=1`、`requires_review=true`、`image_output_enabled=false`。文字 `ready` 不表示旧图片已完成核对。

恢复前备份私有配置、审计、动作、状态及完整桥数据库，再建立隔离记录和关闭图片开关。只启动本项目桥，保留微信会话，并比较 Docker/FRP、宿主网络及 Native 身份基线。
