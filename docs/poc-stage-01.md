# 基础验证步骤与第一次预检结果

## 硬边界

- 不执行 Docker/Compose 命令，不操作 Docker daemon、现有容器或网络。
- 不修改或重启 frpc，不修改其配置、端口、路由或防火墙。
- 不修改现有 AstrBot 配置，不接入现有机器人。
- 不安装系统包，不调整 AppArmor、sysctl 或全局代理设置。
- 第三方程序运行前，必须实测资源限制、文件隔离和网络隔离；任一失败即停止。

共享内核和硬件不能提供绝对零风险保证。这些边界用于尽量隔离测试，并在保护条件不满足时停止，而非以“不会崩溃”的承诺替代验证。

## 拆分后的实现顺序

| 阶段 | 技术猜想 | 最小实验 | 通过标准 |
| --- | --- | --- | --- |
| 0 保护机制 | 测试可被资源、目录和网络边界限制 | 只运行系统自带 Python 探针 | 读回真实 cgroup 上限；隐藏业务目录与 Docker socket；隔离网络生效 |
| 1 空端启动 | 原生 Linux 微信端可在该环境启动 | 固定版本、校验发布文件；无账号、无外网、无宿主端口的短时启动 | 仅在隔离网络内 health 返回 ok；超时或异常后整组退出 |
| 2 登录 | 测试账号可被原生端接受 | 另设有限时、限资源的扫码实验 | 明确登录结果及同步开销；之后停止实验 |
| 3 指定群读取 | 可获得稳定群标识和成员标识 | 仅读取用户指定测试群的一条标记消息 | 群/成员/消息 ID 完整，区分自己和他人、识别 @ |
| 4 指定群发送 | 可准确回复原群 | 经用户明确同意，发送一条固定标记文本 | 只出现在指定群；失败/不确定不重试、不伪报成功 |
| 5 AstrBot 对接 | OneBot 桥可复用已有 AI | 先用模拟协议验证桥；现有 Docker 不得受影响的约束持续有效 | 不自动修改现有实例；若未来确需调整配置，另行列出具体变更并取得用户授权 |

第一阶段不编写或部署完整桥，不实现多媒体、知识库、主动消息或长期运行服务。

## 2026-10-23 实测结果

服务器：Ubuntu 24.04、x86_64、glibc 2.39。约 29 GB 可用内存；内存 PSI 的 some/full 当前均为 0。以下实验只调用系统自带 Python、systemd-run 和已安装 bubblewrap，没有下载或运行微信端。

### 用户级 cgroup 资源限制：通过

独立 transient service 的实际内核控制文件读回：

```text
memory.max      134217728        # 128 MiB
memory.high     100663296        # 96 MiB
memory.swap.max 0
pids.max        16
cpu.max         20000 100000     # 一个核心的 20%
```

设置运行上限 20 秒，实验约 46 毫秒结束；systemd 报告该实验峰值内存不足 1 MiB。

另以系统自带 `sleep 30` 实测超时：独立单元设置 RuntimeMaxSec=2，约 2.202 秒后得到 result=timeout、status=TERM。该单元随后回收，frpc/dockerd/containerd 的 PID 和启动时间再次复核保持相同。这证明本轮的超时退出机制有实际执行，非仅配置读回。

### 用户级文件/网络隔离：未通过

虽然 user service 接受 ProtectHome/PrivateNetwork 等属性，内部 Python 仍能看到用户 SSH 目录、Docker socket 和宿主机网卡。不能把“参数被接受”当作保护已生效。

另一条 bubblewrap 路线在创建私有网络时被拒绝：

```text
bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted
```

没有为此修改服务器权限或放宽全局安全策略。当前不能在该用户级沙箱下继续执行微信端。

### 前后状态复核

- frpc PID `1026310`，启动时间 `2026-10-18 18:49:20`，前后相同；通过该地址的 SSH 连接正常。
- dockerd PID `1201`、containerd PID `949` 及已观察到的端口代理 PID 前后相同。
- 上述结果仅说明这些进程没有被本次测试重启；本轮未调用 Docker API，也未逐一探测容器业务健康状态。
- 四个临时探针单元均已退出并被回收：LoadState=not-found、ActiveState=inactive。
- 复核仍约 29 GB 可用内存，无交换空间占用，内存 PSI 为 0。

## 当前结论

用户随后在自己的终端以 sudo 执行了系统级探针，所有检查均为 true，输出 `SANDBOX_VERIFIED`。动态 UID 为 63635，独立网络仅有 lo；根目录、/usr、/etc 的只读挂载，以及 Docker/containerd 路径屏蔽挂载均通过。耗时约 196 毫秒，峰值内存 2.7 MiB，退出状态 0。

因此阶段 0 已通过。用户级隔离失败的历史记录保留，以免后续误用；阶段 1 必须继续采用已验证的系统级隔离，而不能退回用户级方案。

系统级 transient unit 可以作为下一条隔离验证路径：使用临时 DynamicUser、私有网络、只读文件系统和资源硬上限，只执行系统 Python。它不需要修改现有 Docker、frpc 或永久服务配置。

系统级探针已由用户运行完成。后续 sudo 仅走交互认证；凭据不得写入项目、脚本、环境变量或上传文件。

即便该系统级探针通过，也仅允许进入空账号、无外网的启动实验。扫码是下一阶段：上游登录成功会自动启动账号同步，不能将扫码描述为“只有登录、不会同步”。

下一步见 [空账号启动实验](poc-empty-client.md)。
