# 2026-11-04 / 2026-11-06 agent-wechat v1.4.0 daemon 死锁（两次）

## 概要

v1.4.0 上线后 wx daemon（native daemon，Rust/tokio）发生**两次同签名内部死锁**。桥侧（Python）零缺陷：健康探针如实报告、SSE 泵自动重连、恢复协调器两次冷恢复成功。两次死锁均无用户流量触发。

- 第一次：2026-11-04，SSE 断开窗口 19:20–20:06 UTC（daemon pid 1353836）。当时 received:0 / forwarded:0。
- 第二次：2026-11-06，恶化窗口 13:57–13:59 UTC（daemon pid 32788）。当时群内仅一条文本消息正常走完全链路（14:19 复验时该消息已在恶化前被处理）。

## 死锁签名（两次一致）

- `/version`、`/healthz`（无鉴权）秒回 401 unauthorized（0.0003s）——HTTP 监听线程活着。
- **所有 `/v1/*` 请求（含带合法 token 的 GET）无限挂起**——curl 无超时输出，无限期等待。
- 线程快照：主线程 + 2 个 tokio-rt-worker 全部 `futex_wait_queue`（strace 采样确认 `FUTEX_WAIT_BITSET_PRIVATE|WILLWAIT` 无超时），1 个 worker `ep_poll`。
- daemon netns 内 26174 监听 socket 上请求堆积：`CLOSE-WAIT(Recv-Q 193)` + `ESTAB(Recv-Q 208)`——连接被 accept 但无人读。
- 线程计数骤减：健康时 ~7-10 线程，死锁后仅 4 线程（对比 v1.2.0 同负载形态）。
- 无出站 TCP 等待（排除等 CDN/腾讯服务器）；media-maintenance.timer 正常（排除宿主侧干扰）。

## 定性

- 死锁在 daemon 内部（账号状态锁被永久持有），桥无法观测也无法避免。
- 触发条件未知：两次均无表情包/图片/语音流量，最小触发样本未取得。
- 桥 `native_health_probe` 每 30s 探测 `/v1/accounts`，失败即报 `native_connection:unreachable`——行为正确，如实反映。

## 恢复动作（两次相同，按 docs/reboot-recovery.md）

1. `systemctl stop astrbot-wechat-media-maintenance.timer` → `run_forwarder.py stop` → `session_runtime.py stop` → `systemctl stop astrbot-wechat-session-owner.service`。
2. daemon `kill -9`（futex 死锁对 SIGTERM 无响应）。
3. `run_forwarder.py start` 冷恢复——登录态保持，无新二维码。
4. recovery-startup.json：attempts 累积至 6 后 `awaiting_network`（300s 冷却退避），retryAt 到点自动重试 → online → rebind → ready（第二次全程约 6 分钟）。
