# 计划2：防止自身消息循环

更新：2026-10-27。防循环已验证并部署。用户明确不在中转层实现连续消息缓冲合并，由AstrBot的chat_plus负责；中转层仍逐条转发，保留有界持久队列、限流和去重。

## 已有保护与本轮补齐

- 接收只允许白名单会话、live来源、incoming方向；正文消息记录再次核对方向、账号、会话与发言人。
- 本轮从此前微信已接受的一条发送记录取得真实自身senderId。启动时只执行两次GET：核对accepted发送意图，再核对其本地消息投影。账号、目标会话、投影ID、方向、正文摘要和字节数必须全部匹配项目私有发送审计。不能验证时停止启动，不按昵称猜测、不重新扫码。
- Native接收工作进程丢弃自身senderId，即便事件错误标成incoming，或正文带有`/ai`/原生@，也不会交给AstrBot。发出方向事件直接跳过；事件与消息记录方向不一致时也不会触发模型。
- 可信控制器、持久队列入口、OneBot转换再次检查真实自身senderId。真实微信senderId通过匿名管道传递；保持已部署OneBot的机器人数字ID不变，避免改变AstrBot侧身份。
- 持久化来源消息ID去重；重连、桥重启和重复事件不再产生第二次模型输入。AstrBot同一请求的重试读取已保存回执，不重复向微信发送。结果不明保持不重发策略。
- 不按正文做全局去重。同一用户重复问相同问题、不同成员发送相同正文、用户复述机器人答复，都作为不同来源消息正常处理。
- 状态增加`self_identity_verified`和`loop_guard`计数：`own_sender`、`outgoing_event`、`outgoing_message`、`duplicate_input`、`duplicate_action`。计数不记录聊天正文或真实自身ID。

## 验证范围

- Windows完整回归534项通过，14项POSIX相关测试跳过。
- Linux独立私有回环沙箱100项全部通过，没有调用LLM。实际Native工作进程模拟包含发出方向事件、误标incoming的自身消息、方向冲突消息，并确认下一条用户消息仍完整送达。
- 复用已经验证的同会话路由、去重、长文本和连续回复机制；没有合并消息、缩减输入或增加固定回复次数上限。
- 真实服务器GET身份核验通过；旁路工作进程已清理，原Native身份、宿主网络、命名空间及Docker/FRP业务进程基线不变。
- 仅重启本项目桥后，`self_identity_verified=true`、`ready=true`、`sse=true`、`astrbot_connected=true`，不确定结果0，服务自动重启计数0。原22条已转发记录未重放；此次核验及切换没有产生模型调用或新二维码。
- 上线55秒时控制器约19.2MiB、OneBot约16MiB、Native父slice约70.4MiB，均无OOM。既有资源上限保持不变。
- 自身消息回流及重复动作在合成API/真实工作进程沙箱中验证；本轮没有故意触发线上AI自循环，也没有要求用户额外发送模型测试问题。

此处防循环针对本桥自身消息、重复事件及重复提交。不承诺识别其他账号是否为机器人；其他机器人用自己的真实账号发来新问题时，仍服从白名单及群唤醒规则。

## 操作与安全边界

只读身份预检：

```bash
sudo python3 -I -B /home/bridgeuser/astrbot-wechat/poc-stage-01/probe_loop_guard.py
```

预检只启动本项目32MiB旁路工作进程读取既有记录，不启动SSE、OneBot或发送动作。结束后核对原Native身份、宿主网络及Docker/FRP业务进程不变。

部署切换只重启`astrbot-wechat-forwarder.service`，复用现有Native会话。保留计划1的资源上限、队列上限及单次7天保护期限；不更改Docker、AstrBot、FRP、宿主防火墙、内核模块或路由。

图片输入及核心功能验收已完成，长期稳定性仍待验证。缓冲合并不纳入中转层范围；WebUI与在线编辑另行计划。
